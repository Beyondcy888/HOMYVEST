# U01_03: Backend (Supabase + PDF report + Google Drive)

## 1. How it works
```
Visitor's browser ──insert (public key, insert-only)──▶ Supabase table public.leads
                                                         │ AFTER INSERT trigger (pg_net, secret header from Vault)
                                                         ▼
                                       Edge Function generate-report (service role, server-side)
                                         1. claims the lead          2. builds the PDF (pdf-lib)
                                         3. uploads to Google Drive  4. writes status + Drive link back to the row
                                                         ▲
                              pg_cron every 10 min ──────┘  (retries pending/failed, max 5 attempts)
```
- Phone-only entries from the hero go to `public.lead_starts` (insert-only too). The sales team can see who started but didn't finish.
- The website only ever holds the **publishable (anon) key**. That key is public by design: the database allows it to **insert valid rows only**. It can't read, change or delete anything. Verified with a real Postgres in this kit's tests: insert OK; select, update and delete denied; bad values rejected; spoofed report fields reset; rate limit at 3 leads per phone per 10 minutes.
- The service role key, the Google credentials and the webhook secret live **only** in Supabase (function secrets and Vault). They're never in the website or the repo.

## 4. The PDF report
One A4 page (two if the visitor wrote long answers). It contains:
- HOMYVEST header, submission time (WIB) and a short reference
- Contact: name, phone, a clickable WhatsApp link, website language
- About the property: funding source, then either owns + wants to build, or main need; plus cities
- Land check (only if the calculator was used)
- A **suggested next step** box tailored to the path (build path vs. operations vs. feasibility)
- Source: page, referrer, campaign, device
- A footer with the full lead ID

Language: `REPORT_LANGUAGE` (`en` or `id`, default `en`). File name: `2026-11-21 1432 - Budi Santoso - +6281234567890 - bank loan.pdf`. Samples are rendered by the tests into `qa/tmp/sample-report-en.pdf` and `-id.pdf`. **Open them and look** (`pdftoppm` → PNG if available, or Playwright's PDF viewer).

## 5. Google Drive: two supported setups
The owner picks one with `GDRIVE_AUTH_MODE` (instructions in `HUMAN_SETUP_SUPABASE_AND_GOOGLE_DRIVE.md`):
- **`oauth`, personal Gmail.** A one-time sign-in (`npm run gdrive:auth`) gives a refresh token. Scope `drive.file`: the app can only see files it creates. Reports go to a "HOMYVEST Leads" folder created automatically in the owner's My Drive.
- **`service_account`, Google Workspace with a Shared Drive.** A service account key, plus a folder in a Shared Drive shared with the service account (Content manager). Google doesn't let service accounts store files in a personal My Drive, which is why the personal case uses `oauth`.

## 6. Secrets inventory
| Secret | Where it lives | Who sets it | Public? |
|---|---|---|---|
| `VITE_SUPABASE_URL` | `.env.local` (git-ignored) + host env settings | owner | yes (by design) |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | `.env.local` (git-ignored) + host env settings | owner | yes (insert-only via RLS) |
| `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_URL` (function) | injected by Supabase into the function automatically | nobody | **no** |
| `REPORT_WEBHOOK_SECRET` | Supabase function secrets **and** Vault (`report_webhook_secret`) | owner | **no** |
| Function URL | Vault (`report_function_url`) | owner | not secret, kept in Vault for convenience |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `GOOGLE_REFRESH_TOKEN` | Supabase function secrets (from `supabase/.env.secrets`, git-ignored) | owner | **no** |
| `GOOGLE_SERVICE_ACCOUNT_JSON_B64`, `GDRIVE_FOLDER_ID` | Supabase function secrets | owner | **no** |
| `SUPABASE_ACCESS_TOKEN` (CLI) | owner's shell only | owner | **no** |

## 7. Agent tasks for U1/U6
1. **Install:** `npm install @supabase/supabase-js` and `npm install -D pdf-lib@1.17.1`.
2. **`.gitignore`**, append:
```gitignore
# --- secrets (U01) ---
.env
.env.*
!.env.example
supabase/.env*
!supabase/.env.secrets.example
supabase/.temp/
supabase/.branches/
*.pem
*service-account*.json
*credentials*.json
client_secret*.json
qa/tmp/
```
   Then run `git rm -r --cached --ignore-unmatch .env .env.local supabase/.env.secrets` (it's harmless if they don't exist).
3. **Git hook:** `git config core.hooksPath .githooks` and `chmod +x .githooks/pre-commit`. Then verify: create a dummy file containing `GOOGLE_REFRESH_TOKEN=` followed by `1//0` and 40 letters, stage it, run `node scripts/check-secrets.mjs --staged`, expect a failure, then unstage and delete the file.
4. **npm scripts** (`package.json`):
```json
"check:secrets": "node scripts/check-secrets.mjs --all",
"gdrive:auth": "node scripts/gdrive-auth.mjs",
"supabase:deploy": "supabase db push && supabase functions deploy generate-report --no-verify-jwt"
```
   Add `supabase` as a devDependency (`npm i -D supabase`) so `npx supabase` works for the owner. **Don't run** deploy commands yourself.
5. **Vitest alias** in `vite.config.ts`, so the function's `npm:` import resolves in tests:
```ts
test: {
  environment: 'node',
  include: ['src/**/*.test.ts'],
  alias: { 'npm:pdf-lib@1.17.1': 'pdf-lib' },
},
```
6. **TypeScript** (verified with `tsc --noEmit` in this kit): `npm i -D @types/node`, then in `tsconfig.json` add:
```json
"types": ["vite/client", "node"],
"paths": { "npm:pdf-lib@1.17.1": ["./node_modules/pdf-lib"] }
```
   and `"exclude": ["supabase/functions"]`. `index.ts` uses Deno globals and is never imported by the app. The tests import only `report.ts` and `drive.ts`, which use web-standard APIs and type-check cleanly with the `paths` entry.
7. Copy `reference/leads/*` → `src/lib/leads/`. Run `npm run test`: the 34 lead tests plus the existing ones must pass. Render and look at the sample PDFs.
8. **Never** add real values to any `.env*` file, and never create `.env.local` or `supabase/.env.secrets`. For e2e, inject fake env vars on the command line only (U01_08 §2).

## 8. Owner's manual steps (summary; full guide in `HUMAN_SETUP_SUPABASE_AND_GOOGLE_DRIVE.md`)
Create the Supabase project → put the URL and publishable key in `.env.local` → `npx supabase login` / `link` / `db push` → choose a Drive mode and get its credentials → fill `supabase/.env.secrets` → `npx supabase secrets set --env-file supabase/.env.secrets` → `npx supabase functions deploy generate-report --no-verify-jwt` → add the two Vault secrets in the SQL editor → submit a test lead → see the PDF in Drive → add the two `VITE_` vars to the hosting provider.

## 9. Troubleshooting (also copy into REPORT_U01.md)
| Symptom | Likely cause | Fix |
|---|---|---|
| Form always goes to WhatsApp | `VITE_SUPABASE_*` missing at build time | Add them to `.env.local` / host settings and rebuild |
| Row saved but `report_status` stays `pending` | Vault secrets missing, or function not deployed | Setup step A8 / A7. The cron retries within 10 minutes |
| `report_status = failed`, error mentions `invalid_grant` | Refresh token revoked or expired (app left in "Testing") | Publish the OAuth app, re-run `npm run gdrive:auth`, update the secret |
| Error mentions `storageQuotaExceeded` / `Service Accounts do not have storage quota` | Service account pointed at a personal Drive | Use `oauth` mode, or a Shared Drive folder |
| Error mentions `File not found` for the folder | `GDRIVE_FOLDER_ID` not created by this app (oauth) or not shared with the service account | oauth: leave `GDRIVE_FOLDER_ID` empty. Service account: share the folder as Content manager |
| Need to re-send a report | Any | In the Supabase table editor, set `report_status` to `pending` and `report_attempts` to `0`. The cron picks it up |
